## 2. Geração dos artefatos OSRM

**Confirmado:**
- **Versão do OSRM:** `osrm/osrm-backend:v5.26.0` (imagem Docker oficial), conforme log: `[info] starting up engines, v5.26.0`.
- **Comandos executados** (em `backend/artefatos/osrm/origem/` → artefatos movidos depois para `runtime/`):

```bash
docker run --rm -v "$PWD/origem:/data" osrm/osrm-backend \
  osrm-extract -p /opt/car.lua /data/rio-grande-do-norte.pbf

docker run --rm -v "$PWD/origem:/data" osrm/osrm-backend \
  osrm-partition /data/rio-grande-do-norte.osrm

docker run --rm -v "$PWD/origem:/data" osrm/osrm-backend \
  osrm-customize /data/rio-grande-do-norte.osrm
```

- **Algoritmo:** **MLD** (Multi-Level Dijkstra). Confirmado pelos artefatos `*.osrm.partition`, `*.osrm.cells`, `*.osrm.mldgr` e pela execução do `osrm-partition` + `osrm-customize`. **Não foi usado CH** (`osrm-contract`).
- **Parâmetros:** apenas `-p /opt/car.lua` no extract. Nenhuma flag extra de partição (defaults: `128 1.2 0.25 10 1000`).
- **Tempo de processamento:** extract ~4,3 s; partition ~34 s; customize ~1,4 s. RAM de pico no extract: ~600 MB; no customize: ~213 MB.

## 4. Matrizes de referência
**Confirmado:**
- **Geração:** chamada direta ao `/table/v1/driving`, **sem script wrapper**. O `04-matriz.sh` original foi descartado por não se adequar ao path (`artefatos/osrm/` sem `scripts/`). Comando efetivo:

```bash
COORDS=$(jq -r 'map("\(.lon),\(.lat)") | join(";")' /tmp/pontos_a3_v2.json)
curl -s "http://localhost:5000/table/v1/driving/${COORDS}?annotations=distance,duration" \
  > osrm/referencias/matriz_a3-lotes-02-15-v2.json
```
- **Origem das coordenadas:** `a3-lotes-02-15-v2.json` → `.registros[]`, na **ordem do array**. **A ordem dos `registros` é a ordem dos índices da matriz.**
- **Formato:** `longitude,latitude` (padrão GeoJSON, exigido pelo OSRM). Coordenadas no sistema WGS84.
- **Unidades:** `distances` em **metros**, `durations` em **segundos**.
- **Valores ausentes:** representados como **`null`** no JSON (quando um ponto não faz snap na malha). Na matriz v2, **0 nulls**.
- **Mapeamento índice ↔ atividade:** `matriz.distances[i][j]` corresponde a `registros[i] → registros[j]`. O arquivo `a3-lotes-02-15-v2.json` tem `id` e `nome` em cada registro, permitindo o mapeamento reverso.
**Não há geração de matriz direcionada "1 ponto novo + 132"** — isso **não foi feito** nos artefatos atuais. A matriz existente é 132×132 simétrica nos índices, assimétrica nos valores (mão única).

## 5. Diferenças entre as versões das matrizes
**Confirmado:**
| Arquivo | O que é |
|---|---|
| `matriz_a3-lotes-02-15.json` (v1) | Matriz 132×132 gerada a partir do `a3-lotes-02-15.json` (coordenadas originais) |
| `matriz_a3-lotes-02-15-v2.json` (v2) | Matriz 132×132 gerada a partir do `a3-lotes-02-15-v2.json` (7 coords substituídas) |
| `*_distancias.txt` / `*_duracoes.txt` | Versões formatadas (TSV + `column -t`) das respectivas matrizes |

**Motivação da v2:** sete atividades (índices `31, 33, 39, 40, 58, 59, 60`) tinham coordenadas originais em áreas sem via veicular mapeada — praias, dunas, interior da Fortaleza dos Reis Magos. O OSRM fazia snap automático para o acesso veicular mais próximo (distâncias de 100 a 522 m). A v2 **substituiu as coordenadas originais pelas coordenadas do snap**, tornando explícito no dado de entrada o ponto de roteamento efetivamente usado.
**Resultado da mudança:**
- **As matrizes v1 e v2 são numericamente idênticas** — confirmado por `diff` direto dos arrays `.distances` (resultado vazio). Isso ocorre porque o OSRM **já calculava rotas a partir do snap**, não da coordenada original. A v2 só torna explícito o que já acontecia.
- **Não houve correção de valores**, apenas de representação.
**Versão de referência:** **`matriz_a3-lotes-02-15-v2.json`** (e seus `.txt`). Motivo: é a versão que documenta a decisão de normalização, coerente com o `RELATORIO_VALIDACAO.md`. A v1 é mantida apenas como registro histórico.

## 7. Integração com o backend (FastAPI)
**Premissa:** módulo `routing` em Python/FastAPI consome o OSRM em `http://localhost:5000` (ou host configurável).
### 7.1 Envio de coordenadas
- **Ordem obrigatória:** `longitude,latitude` (não `lat,lon`).
- **Separador:** `;` entre pontos.
- **Exemplo:** `/route/v1/driving/-35.2089,-5.8745;-35.1837,-5.8327`
### 7.2 Matriz completa entre 1 ponto novo e os 132
**Não existe** matriz pré-calculada para isso nos artefatos atuais. Para gerar:
```python
import httpx

PONTOS_132 = [...]  # lê de a3-lotes-02-15-v2.json → .registros

async def matriz_ponto_novo_para_132(lon: float, lat: float) -> dict:
    coords = ";".join(f"{r['lon']},{r['lat']}" for r in PONTOS_132)
    coords += f";{lon},{lat}"
    url = f"http://localhost:5000/table/v1/driving/{coords}"
    async with httpx.AsyncClient(timeout=30.0) as client:
        r = await client.get(url, params={"annotations": "distance,duration"})
        r.raise_for_status()
        return r.json()
    # resultado: distances[132][0..131] = novo → cada um
    #           distances[0..131][132] = cada um → novo
```
**Alternativa para 1 ponto só:** usar `/route` para cada par (mais lento, mas sem `--max-table-size` alto).
### 7.3 Matriz 132×132 já pronta
**Recomendado:** **ler o arquivo** `matriz_a3-lotes-02-15-v2.json` — não chamar `/table` de novo. O arquivo tem 287 KB, carrega em milissegundos, e é determinístico.
```python
import json
with open("artefatos/osrm/referencias/matriz_a3-lotes-02-15-v2.json") as f:
    m = json.load(f)
# m["distances"][i][j], m["durations"][i][j]
```
**Só use `/table` em runtime** se os pontos forem arbitrários (não os 132).
### 7.4 Tratamento de erros
- **`code: "Ok"`** → sucesso.
- **`code: "NoRoute"`** → par sem rota viável (raro no RN). Tratar como `None`/`inf`.
- **`code: "TooBig"`** → número de coordenadas > `--max-table-size`. Subir o limite no container **ou** quebrar em lotes.
- **`code: "InvalidQuery"`** → coordenada malformada (ex.: `null,null`). Validar antes de enviar.
- **HTTP 400/500** → erro do servidor. Fazer retry com backoff (até 3 tentativas) e logar.
- **Timeout** → subir `--max-table-size` **não** resolve; aumentar timeout do cliente (httpx) para 30–60 s em matrizes grandes.
### 7.5 Limites de coordenadas por requisição
- **Default OSRM:** 100 pontos por chamada.
- **Configurado no container:** `--max-table-size 200` (cobre 132 + margem).
- **Custo:** memória cresce **quadraticamente** com N (200² = 40k pares; 500² = 250k pares). Se for usar muitos pontos simultâneos, monitorar RAM.
- **Para > 200 pontos:** subir `--max-table-size` **ou** quebrar em lotes de 100 e concatenar (mais eficiente em memória).
### 7.6 Cuidados de compatibilidade
- **A matriz v2 foi gerada com `--max-table-size 200`** — se o backend rodar com `--max-table-size 100` (default), `/table` com 132 pontos falha. **Garantir que o container de produção use ≥ 200.**
- **A matriz v2 foi gerada com o `rio-grande-do-norte.osrm`** (mesmos artefatos em `runtime/`). **Não trocar o PBF** sem regerar a matriz.
- **A matriz v2 é imutável** — se o PBF for atualizado, a matriz precisa ser regerada.
- **`http://localhost:5000`** funciona se o backend roda no host. Se roda em container, usar o nome do serviço Docker (`http://osrm:5000`) e configurar rede compartilhada.
